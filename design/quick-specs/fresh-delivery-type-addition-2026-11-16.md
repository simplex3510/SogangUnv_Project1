# Quick Design Spec: Fresh 배송 유형 도입

**Type**: Addition
**System**: 배송 유형 / 배송 제한 시간 / 보상 (Delivery Type)
**GDD Reference**: `design/gdd/game-concept.md` 6.2·7장·11장, `design/gdd/delivery-cargo-vehicle-rules.md` 2장
**Date**: 2026-11-16
**Status**: 확정 (2026-11-16, `game-concept.md` 1.8에 반영. 두 문서가 다르면 `game-concept.md`가 우선한다)

## Change Summary

Express보다 시간 조건이 엄격하고 보상이 큰 세 번째 배송 유형 **Fresh(신선 배송)**를 추가한다. Fresh의 제한 시간은 "신선도"이며 **상차 후부터** 줄어든다. 보상은 배송할 때 남아 있는 신선도에 비례한다. 신선도가 다 떨어지면 물류는 **폐기 물류**가 되어 적재 공간을 계속 차지하고, 지정된 **처분 장소**에서 비워야 한다.

## Motivation

- Express는 생성 시점부터 시간이 흘러서 "언제 출발할까"보다 "얼마나 빨리 처리할까"만 묻는다. Fresh는 상차 시점부터 시간이 흐르므로 **언제 실을지**와 **무엇과 함께 실을지**를 판단하게 만든다(1.2 핵심 재미: 배송 계획).
- 보상이 남은 시간에 따라 연속으로 줄어들기 때문에, 성공·실패 두 가지 결과만 있는 Express와 달리 경로 효율이 그대로 수익에 반영된다.
- 폐기 물류는 "실패해도 끝이 아니라 처리할 짐이 남는" 리스크를 만든다. 그래서 고보상과 실패 부담 사이에서 선택하게 된다.

## Design Delta

Current GDD says (`game-concept.md` 6.2):

> | 신속 배송 | Express | 있음(거리 기반, 7장) | 제한 시간 내 완료 시 지급 | 제한 시간 초과 후 완료 시 적용 |
> - 제한 시간 초과는 배송 실패가 아니다. 배송 성공·실패는 영업 종료 시점까지 배송을 완료했는지로만 판정한다(11장).

Current GDD says (`game-concept.md` 7.2):

> - Express 물류는 생성되는 시점부터 배송 제한 시간이 감소한다.

This spec changes that to:

- 배송 유형을 3개로 늘린다(Normal / Express / **Fresh**).
- Fresh에만 다음 예외를 둔다.
  - 시간 감소 시작 시점: 상차 완료 시점
  - 보상: 남은 시간 비례
  - 초과 시: 폐기 전환, 즉시 배송 실패
- 즉, "제한 시간 초과는 배송 실패가 아니다"는 규칙은 **Express에만** 적용된다.

## New Rules / Values

### 1. 유형 정의

| 배송 유형 | 식별자 | 제한 시간 | 시간 감소 시작 | 시간 보상 | 초과 시 |
|---|---|---|---|---|---|
| 일반 배송 | Normal | 없음 | — | 없음 | — |
| 신속 배송 | Express | 있음 | 물류 생성 시점 | 제한 시간 내 완료 시 고정 지급 | 시간 초과 손실, 배송은 가능 |
| **신선 배송** | **Fresh** | **있음(신선도)** | **상차 완료 시점** | **남은 신선도 비례 지급** | **폐기 물류로 전환, 배송 실패** |

- 기본 배송료, 거리 추가 배송료, 물류 특징 보상은 Fresh에도 똑같이 지급한다(배송을 완료한 경우).
- 생성 확률은 `DeliveryTypeConfig`에서 관리하고, 정적·동적 생성 모두 같은 확률을 쓴다(6.2 기존 규칙 유지).

### 2. 신선도(제한 시간) 산정

```
T_fresh = T_base(D) * M_fresh + R
```

- 산식은 Express(7.1)와 같다. 엄격함은 계수로 조정한다: `M_fresh < M_express`.
- 물류를 생성할 때 계산해 저장한다(생성 시점 고정 원칙 유지). **흐르기 시작하는 시점만** 상차 완료 시점이다.

### 3. 신선도 감소

1. 물류센터에서 대기하는 동안(`Pending`)에는 신선도가 줄지 않는다.
2. 물류 1개의 상차가 **완료된 순간**부터 그 물류의 신선도가 줄기 시작한다. 그룹으로 상차하면 물류마다 시작 시점이 다르다.
3. 상차한 뒤에는 이동, 하차 진행, 처분 장소 체류 중에도 게임 시간 기준으로 계속 줄어든다.
4. `남은 신선도 = T_fresh − (현재 게임 시각 − 상차 완료 시각)`

### 4. 보상 (신선도 보상)

```
B_fresh_earned = B_fresh * clamp(T_remain / T_fresh, 0, 1)
```

| 변수 | 설명 |
|---|---|
| B_fresh_earned | 실제 지급하는 신선도 보상 |
| B_fresh | Fresh 최대 신선도 보상. Express 시간 추가 보상보다 크게 둔다 |
| T_remain | 하차를 완료한 순간의 남은 신선도 |
| T_fresh | 그 물류의 신선도 총량 |

- 예: `B_fresh` 200, 신선도 120초 중 90초가 남았을 때 배송 → 200 × 0.75 = **150**
- 감소 형태는 **선형**으로 제안한다(미확정). 구간 단계형(100/70/40%)이 대안이다.

### 5. 폐기 물류 (Spoiled)

> **2026-11-16:** 5·6·8항은 내구도 0과 함께 쓰는 **폐기 물류 공통 규칙**으로 확정되어 `game-concept.md` 11.6으로 이관했다. 아래 내용과 11.6이 다르면 11.6이 우선한다. Fresh 고유 부분은 "신선도 0이 폐기 원인"이라는 점과 실패 페널티 계수(`M_fail,fresh`)뿐이다.

1. 남은 신선도가 0이 되는 순간, 물류 상태가 `Loaded`에서 **`Spoiled`(폐기)**로 바뀐다.
2. 이 시점에 **배송 실패가 확정**되고, 배송 실패 페널티 `P * M_fail,fresh`를 매긴다. 정산에는 실패 항목으로 집계한다.
   - 시간 초과 손실은 적용하지 않는다. 16.1-4 "중복 적용 없음" 원칙과 같다.
3. ~~폐기 물류는 배송지에 하차할 수 없다. 하차 대상, 배송지 아이콘, 나침반 목표에서 제외한다.~~ → 2026-11-16 수정: 목적지가 처분 장소로 재설정되고, UI·아이콘·나침반은 처분 장소를 가리킨다(`game-concept.md` 11.6 규칙 3).
4. 폐기 물류는 처분하기 전까지 **적재 한도와 무게 한도를 그대로 차지한다**(리스크).
5. 하차가 진행되는 중에 0이 되면 그 물류의 하차를 중단한다. 진행도는 초기화하고 바로 폐기로 전환한다.

### 6. 처분 장소 (Disposal Site)

- 새 상호작용 대상이다. 2.2의 물류센터·배송지에 이어 세 번째다.
- 처분 장소에서 상호작용 키를 누르고 있으면 실려 있는 폐기 물류를 1개씩 처분한다. 물류 1개마다 처분 소요시간이 걸린다.
- 처분된 물류는 차량에서 빠지고, 적재 한도와 무게 한도가 회복된다.
- 처분할 때 보상이나 비용은 없다. 리스크는 이동 시간과 적재 공간 손실뿐이다(제안, 처분 비용 도입 여부는 미확정).
- 폐기 물류가 없으면 처분 장소와 상호작용할 수 없다. 상호작용 키를 누르면 "처분할 물류 없음"을 표시한다(16.2-6과 같은 방식).
- 처분 장소의 위치와 개수: 1차 맵에 1곳(제안). 물류센터에서 떨어진 곳에 두어 우회 비용이 생기게 한다.

### 7. 처리 순서 (7.4 개정 제안)

같은 배송지에 할당된 물류는 다음 순서로 처리한다.

1. Fresh(상차됨): 남은 신선도가 짧은 순서
2. Express: 남은 제한 시간이 짧은 순서
3. Normal: 생성 순서
4. 물류센터에서 대기 중인 Fresh는 신선도가 흐르지 않으므로, Express 다음 자리에서 **신선도 총량이 짧은 순서**로 둔다(제안).

### 8. 하루 종료

- 영업 종료 시 이미 폐기된 물류는 실패가 확정돼 있으므로 페널티를 다시 매기지 않는다. 차량에 남은 폐기 물류는 그냥 정리한다.
- 상차하지 않은 Fresh, 상차했지만 아직 신선한 Fresh는 기존 미배송 규칙(11.4)대로 배송 실패로 처리한다.

### 9. UI

| 위치 | 표시 |
|---|---|
| 물류센터 행 | 유형 태그 `FRS`. 만료 시각 대신 신선도 총량을 모래시계 아이콘 + `hh:mm 남음`(게임 시간)으로 표시하고, 바는 가득 찬 채로 고정. Express는 시계 아이콘 + `hh:mm까지` (2026-11-18 개정, 이전 `↻2:00`) |
| 상차 후(배송지 아이콘, HUD) | 신선도 바가 줄어듦. HUD 적재 패널 행은 바 오른쪽에 모래시계 + `hh:mm 남음`이 함께 줄어듦 (2026-11-18 추가) |
| 폐기 물류 | 회색·폐기 아이콘. 처분 장소 방향을 나침반에 추가 |
| 정산 | `FRESH BONUS`(받은 신선도 보상 합계), 폐기 건수는 실패 항목에 포함 |

## Acceptance Criteria

- [ ] Fresh 물류가 생성 로그에 `Fresh`로 나오고, 신선도 총량이 같은 거리의 Express 제한 시간보다 짧다.
- [ ] 물류센터에서 대기하는 동안 Fresh의 남은 신선도가 줄지 않는다(게임 시간 1시간 경과 전후로 같은 값).
- [ ] 상차가 완료된 순간부터 그 물류의 신선도가 줄어든다. 그룹 상차 시 물류마다 시작 시각이 다르다.
- [ ] 남은 신선도가 50%일 때 배송하면 신선도 보상이 `B_fresh × 0.5`(±1)로 정산된다.
- [ ] 신선도가 0이 되면 상태가 `Spoiled`가 되고, 배송지에서 하차할 수 없으며, 적재·무게 사용량이 그대로 유지된다.
- [ ] 폐기 시점에 실패 페널티가 한 번만 기록되고, 영업 종료 시 다시 기록되지 않는다.
- [ ] 처분 장소에서 폐기 물류를 처분하면 적재 사용량이 그만큼 줄어든다. 폐기 물류가 없으면 "처분할 물류 없음"을 표시한다.
- [ ] No regression: Normal·Express의 생성, 제한 시간, 보상, 정산 결과가 기존과 같다(7.6 R6 검증 시나리오 재실행).
