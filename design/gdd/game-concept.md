# 1. 게임 개요

## 1.1. 게임 콘셉트

플레이어가 운송 차량을 직접 조작하여 물류센터에서 물류를 상차하고, 각 물류에 지정된 배송지까지 운송한 뒤 하차하는 캐주얼 배달 운송 시뮬레이터이다.

플레이어는 물류센터에서 배송할 물류를 선택하고, 차량의 적재 한도·무게 한도와 각 물류의 배송 유형·특징·배송 제한 시간을 고려하여 배송 계획을 세운다. 이후 차량을 직접 운전하여 여러 배송지를 방문하고 배송을 완료한다.

배송 완료를 통해 수익을 획득하며, 장기적으로는 획득한 수익을 활용하여 차량과 물류센터의 능력을 개선하고 더욱 효율적인 배송을 수행하는 것을 목표로 한다.

현재 마일스톤에서는 기본 배송 루프와 배송 과정에서 발생하는 조작 및 판단의 재미를 검증하는 데 집중한다. 성장 및 업그레이드 시스템은 후속 개발 범위로 둔다.

## 1.2. 게임 핵심 재미

### 핵심 재미

1. **배송 과정 전체의 재미**
   - 물류 선택, 상차, 운송, 배송, 하차로 이어지는 전 과정을 직접 수행한다.
   - 배송지별 물류량과 배송 제한 시간을 고려하여 배송 순서를 결정한다.

2. **차량 조작의 통제감**
   - 플레이어가 직접 차량을 조작하여 원하는 경로로 이동한다.
   - 장애물과 도로 환경에 대응하며 목적지에 도달한다.

3. **배송 계획 및 판단**
   - 차량의 적재 한도와 무게 한도, 물류 특징(대형·고중량)을 고려하여 물류를 선택한다.
   - 신속 배송(Express) 물류의 남은 배송 제한 시간을 고려하여 상차 및 하차 우선순위를 결정한다.
   - 배송지 방문 순서를 직접 결정한다.

4. **배송 완료와 성취감**
   - 신속 배송을 제한 시간 내 완료하거나 특징이 붙은 물류를 배송하여 추가 보상을 획득한다.
   - 배송을 반복하여 하루의 운영 목표를 달성한다.

### 보조 재미

- 고정 장애물과 같은 환경적 방해 요소를 극복하는 재미
- 후속 업데이트에서 도입할 수 있는 경찰 추격 시스템의 긴장감

경찰 추격 시스템은 현재 마일스톤의 범위에 포함하지 않는다.

## 1.3. 핵심 게임 루프

```text
물류센터에서 배송 물류 확인
        ↓
배송할 물류 선택
        ↓
차량에 물류 상차
        ↓
배송 경로 및 순서 판단
        ↓
차량 운전 및 배송지 이동
        ↓
배송지에서 물류 하차
        ↓
배송 보상 획득
        ↓
남은 물류 배송 또는 물류센터 재방문
        ↓
하루 운영 종료 또는 모든 배송 완료
        ↓
일일 정산
```

플레이어는 정해진 배송 경로를 따라가는 것이 아니라, 현재 적재된 물류와 배송 제한 시간을 고려하여 배송 순서를 자유롭게 결정한다.

# 2. 플레이어 조작 및 상호작용

## 2.1. 기본 조작

| 입력 | 기능 |
|---|---|
| ↑ | 전진 입력 |
| ← | 좌회전 입력 |
| ↓ | 후진 입력 |
| → | 우회전 입력 |
| ctrl | 주행 모드 전환 |
| shift | 드리프트 (회전 입력 필요) |
| Spacebar | 상호작용 |
| R (홀드) | 차량 복구(리셋, 10.6) |

차량 이동과 관련된 세부 조작 감도 및 물리 수치는 밸런싱 및 구현 단계에서 조정한다.

## 2.2. 상호작용 대상

상호작용 대상 건물은 다음 세 가지로 구성한다.

| 대상 | 기능 |
|---|---|
| 물류센터 | 배송 물류 확인 및 상차 |
| 배송지 | 해당 배송지에 할당된 물류 하차 |
| 처분 장소 | 차량에 실린 폐기 물류 처분(11.6) |

상호작용 키(기본 Spacebar)는 상호작용 대상에 접근하여 UI를 호출하는 기능과 상호작용 작업을 수행하는 기능으로 사용한다.

상호작용 작업은 상호작용 키를 누르고 있는 동안 진행되며, 작업 대상 및 상황에 따라 상차 또는 하차를 수행한다.

# 3. 하루 운영 및 게임 시간 시스템

## 3.1. 기본 운영 시간

하루 운영은 게임 내 시간 기준으로 진행한다.

| 항목 | 기본값 | 설정 정책 |
|---|---:|---|
| 영업 시작 시각 | 09:00 | Unity Editor에서 변경 가능 |
| 영업 종료 시각 | 18:00 | Unity Editor에서 변경 가능 |
| 동적 물류 생성 마감 | 16:00 | 영업 종료 시각 2시간 전 |
| 첫 동적 물류 생성 가능 시각 | 09:00 | Unity Editor에서 변경 가능 |

실제 운영 시간은 Unity Editor에서 조정할 수 있도록 구성한다.

동적 물류 생성 마감은 별도 고정 시각보다는 영업 종료 시각에서 2시간을 차감하여 계산한다.

`DynamicSpawnEndTime = BusinessEndTime - 2 hours`

## 3.2. 게임 시간 진행

- 게임 시간은 현실 시간보다 빠르게 진행한다.
- 시간 배속은 고정값을 사용한다.
- 플레이어는 게임 내 시간 배속을 변경할 수 없다.
- 현재 마일스톤에서는 일시정지 및 시간 배속 변경 기능을 제공하지 않는다.
- 배송 제한 시간, 동적 물류 생성 및 하루 종료는 동일한 게임 시간 기준을 사용한다.
- 상차 및 하차 중에도 게임 시간은 정상적으로 진행된다.
- 상차 및 하차 중에도 물류의 배송 제한 시간은 감소한다.
- 하루 운영 중에는 어떤 UI를 열어 두어도(물류센터 상차 UI, 적재 물류 UI, 처분, 복구 진행 등) 게임 시간과 물류 제한 시간이 멈추지 않는다(2026-11-16 확정). 정산 화면은 하루 종료 이후이므로 해당하지 않는다.

시간 배속은 현실 1초당 게임 60초(현실 1초 = 게임 1분)로 시작한다. 기본 운영 시간(9시간) 기준 하루는 현실 9분이다(2026-11-16 확정). 최종 수치는 16.4에서 조정한다.

## 3.3. 게임 시간 UI

게임 플레이 화면 좌상단에 현재 일차와 게임 내 시각을 표시한다(2026-11-17 확정).

- 표시 형식: `DAY N  HH:mm`
- 예시: `DAY 1  09:30`, `DAY 1  14:45`
- 일차는 1부터 시작한다. 여러 날 진행이 생기기 전까지는 항상 `DAY 1`이다.
- 영업 종료까지 남은 시간은 별도로 표시하지 않는다.
- 게임 시간은 내부적으로 프레임마다 연속 진행하는 초 단위 실수다. 모든 시간 판정은 이 연속 값으로 한다. 시계 표시는 게임 1분 단위로 바뀐다(초는 버림)(2026-11-16 확정).
- 정산 화면에서는 게임 내 시계를 표시하지 않는다.

개별 물류의 배송 제한 시간은 물류별 프로그레스 바로 확인할 수 있다.

## 3.4. 하루 시작 처리

하루가 시작되면 다음 순서로 초기화한다.

1. 게임 내 시각을 영업 시작 시각으로 설정한다.
2. 하루 운영 관련 데이터를 초기화한다.
3. 배송지별 일일 누적 할당량을 초기화한다.
4. 하루 동적 물류 생성 가능량을 결정한다.
5. 정적 물류 생성량을 결정한다.
6. 정적 물류를 생성하고 배송지에 할당한다.
7. 정적 물류 생성이 완료되면 플레이어 조작을 활성화한다.

정적 물류가 모두 준비되기 전에는 플레이어가 게임을 시작할 수 없다.

## 3.5. 하루 종료 조건

하루 운영 종료 조건은 다음 두 가지이다.

### 조건 1. 영업 종료 시각 도달

게임 내 시계가 영업 종료 시각에 도달하면 즉시 하루 운영을 종료한다.

- 차량 이동을 중단한다.
- 진행 중인 상차 및 하차 작업을 중단한다.
- 물류센터 및 배송지 상호작용을 종료한다.
- 배송이 완료되지 않은 물류를 미배송 처리한다.
- 일일 정산 화면으로 전환한다.

영업 종료 시점에 하차가 진행 중이더라도 실제 하차 완료 판정이 이루어지지 않았다면 미배송으로 처리한다.

### 조건 2. 모든 배송 완료

하루에 처리해야 할 모든 배송이 완료되면 영업 종료 시각에 도달하지 않았더라도 하루 운영을 조기 종료한다.

**중요:** 배송지별 일일 할당 한도 소진은 하루 조기 종료 조건이 아니다. 할당 한도 소진은 해당 배송지에 신규 물류를 더 이상 할당할 수 없다는 의미이다.

## 3.6. 하루 종료 이후

- 일일 정산 화면으로 전환한다.
- 정산 화면에서는 게임 내 시계를 표시하지 않는다.
- 다음 운영이 시작될 경우 게임 내 시각은 영업 시작 시각으로 초기화한다.
- 현재 마일스톤에서는 다음 날 운영 및 물류 이월 기능을 구현하지 않는다.

## 3.7. 같은 프레임의 시간 이벤트 처리 순서 (2026-11-16 확정)

한 프레임 안에서 시간 관련 사건이 겹치면 다음 순서로 처리한다. 경계 시각에 도달한 순간 그 시각의 판정을 먼저 적용한다(시간 판정 우선).

1. 게임 시간 진행
2. 영업 종료 판정(3.5). 종료되면 이후 단계를 처리하지 않는다
3. 동적 물류 생성 마감 판정(4.2). 현재 시각이 마감 시각 이상이면 생성을 중단한다. 마감 시각 정각에는 생성하지 않는다
4. 동적 물류 생성(4.2). 한 프레임에 최대 1개만 생성한다
5. Express 제한 시간·Fresh 신선도 감소와 초과·소진 판정(7장)
6. 상차·하차·처분 완료 판정(8~11장)

- 하차 완료와 Express 제한 시간 초과가 같은 프레임이면 초과가 먼저 적용되어 시간 초과 후 완료로 처리한다(11.3).
- 하차 완료와 Fresh 신선도 0이 같은 프레임이면 폐기 물류 전환이 먼저 적용되어 하차가 중단된다(7.3·11.6).
- 영업 종료와 하차 완료가 같은 프레임이면 미배송으로 처리한다(3.5).

# 4. 물류 생성 시스템

물류는 생성 시점에 따라 정적 생성(Static)과 동적 생성(Dynamic) 두 가지 생성 방식으로 구분한다.

생성 방식은 배송 유형(6.2) 및 물류 특징(6.3)과 독립된 분류 축이며, 각 물류 데이터에 기록한다.

## 4.1. 정적 물류 (Initial Deliveries)

정적 물류는 하루 운영 시작 시 사전에 생성되는 기본 물류이다.

### 생성 규칙

- 하루 시작 시 생성한다.
- 생성량은 설정된 최소·최대 범위 내에서 무작위로 결정한다.
- 생성된 물류는 배송지에 무작위로 할당한다.
- 배송지별 일일 누적 할당 한도를 적용한다.
- 정적 물류 생성량이 배송지 전체 잔여 할당량을 초과하면 잔여 할당량까지만 생성한다.
- 동적 물류와 동일한 배송 유형 생성 확률과 물류 특징 생성 확률을 적용한다.
- 물류 생성이 완료된 이후 플레이어 조작을 활성화한다.

정적 물류 생성량은 Unity Editor에서 조정할 수 있도록 한다.

## 4.2. 동적 물류 (Dynamic Deliveries)

동적 물류는 하루 운영 중 무작위 시점에 추가로 생성되는 물류이다.

### 생성 규칙

- 하루 시작 시 동적 물류의 하루 생성 가능량을 최소·최대 범위 내에서 무작위 결정한다.
- 첫 생성 가능 시각은 별도 설정값으로 관리한다.
- 첫 생성 가능 시각의 기본값은 영업 시작 시각인 09:00이다.
- 첫 생성 이후의 물류 생성 간격은 설정된 최소·최대 범위 내에서 무작위로 결정한다.
- 다음 생성 시각은 이전 물류의 실제 생성 시점을 기준으로 계산한다.
- 동적 물류는 영업 종료 2시간 전부터 신규 생성을 중단한다.
- 기본 운영 시간 기준 생성 마감은 16:00이다.
- 동적 물류 생성은 배송지별 일일 누적 할당 한도를 공유한다.
- 하루 생성 가능량은 생성에 성공할 때마다 1씩 차감한다.
- 정적 물류와 동일한 배송 유형 생성 확률과 물류 특징 생성 확률을 적용한다.
- 동적 물류가 생성되면 토스트 알림으로 알린다(13장, 2026-11-17 확정). 정적 물류(하루 시작 시 생성)는 알리지 않는다.

### 동적 물류 생성 실패

동적 물류 생성 시 할당 가능한 배송지가 존재하지 않는다면 해당 생성은 취소한다.

이 경우:

- 다른 배송지를 재검색하거나 대기열에 등록하지 않는다.
- 생성 실패 이후 재시도하지 않는다.
- 동적 물류 생성 시스템 자체를 종료한다.
- 기존에 생성된 물류의 배송 및 상차에는 영향을 주지 않는다.

동적 물류 생성 시스템의 종료는 하루 운영의 종료를 의미하지 않는다. 플레이어는 기존 물류를 계속 배송할 수 있다.

## 4.3. 동적 물류 생성 마감 이후

동적 물류 생성 마감과 물류센터 운영 종료는 별개의 규칙으로 처리한다.

| 기능 | 생성 마감 이후 ~ 영업 종료 이전 |
|---|---|
| 신규 동적 물류 생성 | 중단 |
| 기존 물류 확인 | 가능 |
| 기존 물류 상차 | 가능 |
| 배송지 방문 | 가능 |
| 물류 하차 | 가능 |
| 배송 제한 시간 감소(Express) | 계속 진행 |

동적 물류 생성이 중단되더라도 물류센터의 상차 기능은 영업 종료 전까지 정상적으로 이용할 수 있다.

# 5. 배송지 할당 시스템

## 5.1. 배송지별 일일 할당 한도

각 배송지는 하루 동안 할당받을 수 있는 물류의 최대 개수를 가진다.

배송지별로 다음 데이터를 관리한다.

| 데이터 | 설명 |
|---|---|
| DailyAssignedCount | 당일 누적 할당 물류 개수 |
| MaxDailyAssignmentCount | 하루 최대 할당 가능 개수 |

배송지가 물류를 할당받을 때 `DailyAssignedCount`를 1 증가시킨다.

배송 완료 여부와 관계없이 누적 할당량은 감소하지 않는다.

즉, 물류를 배송 완료해도 배송지의 일일 할당 가능량은 복구되지 않는다.

## 5.2. 배송지 할당 규칙

물류가 생성될 때 할당 가능한 배송지 중 하나를 무작위로 선택한다.

할당 가능한 배송지는 다음 조건을 만족해야 한다.

`DailyAssignedCount < MaxDailyAssignmentCount`

할당 규칙:

- 정적 물류와 동적 물류는 동일한 할당 규칙을 사용한다.
- 현재 할당 가능한 배송지 후보 중 하나를 균등 확률로 선택한다.
- 배송지별 잔여 할당량에 따른 가중치는 적용하지 않는다.
- 일일 할당 한도가 소진된 배송지는 후보에서 제외한다.
- 배송지별 할당 한도를 초과하여 물류를 배정할 수 없다.

## 5.3. 할당 한도 소진 처리

모든 배송지의 일일 할당 한도가 소진되면 신규 물류를 할당할 수 없다.

이 상태는 신규 동적 물류 생성의 실패 조건이 될 수 있으며, 해당 조건으로 동적 물류 생성 시스템이 종료될 수 있다.

그러나 할당 한도 소진 자체는 하루 운영 종료 조건이 아니다.

이미 생성된 물류가 남아 있다면 플레이어는 해당 물류의 배송을 계속 수행해야 한다.

하루 조기 종료는 모든 배송이 완료되었을 때만 발생한다.

# 6. 물류 데이터, 배송 유형, 물류 특징

## 6.1. 물류 데이터

각 물류는 독립적인 데이터로 관리한다.

주요 데이터 항목은 다음과 같다.

| 데이터 영역 | 항목 |
|---|---|
| 식별 및 할당 | 물류 고유 식별자, 할당된 배송지 |
| 배송 조건 | 배송 유형, 배송 제한 시간·남은 제한 시간·시간 초과 여부(Express만) |
| 생성 정보 | 생성 방식(Static/Dynamic), 생성 시각 |
| 물류 특징 | 부여된 특징(`Fragile`, `Heavy`, `Large`, 복수 가능) |
| 물류 프로퍼티 | 내구도(Durability): 초기 내구도·현재 내구도(6.4) |
| 적재 사용량 | 적재 용량 사용량, 무게 적재량 |
| 진행 상태 | 배송 진행 상태 |
| 보상 정보 | 기본 배송료, 거리 추가 배송료, 시간 추가 보상, 물류 특징 보상, 시간 초과 손실, 배송 실패 페널티 |

배송 유형, 생성 방식, 물류 특징은 서로 다른 분류 축이며 자유롭게 조합된다(예: Express + Dynamic + Fragile·Large).

배송 제한 시간, 적재 사용량, 초기 내구도, 보상 관련 데이터는 물류 생성 시점에 결정하여 해당 물류 데이터에 저장한다.

이를 통해 물류 생성 이후 설정값이 변경되더라도 이미 생성된 물류의 조건이 임의로 변경되지 않도록 한다. 단, 현재 내구도는 예외로 충돌에 따라 감소한다(6.4).

## 6.2. 배송 유형 (Delivery Type)

배송 유형은 물류를 배송지까지 운송·인도하는 배송 서비스의 시간 조건을 정의한다. 물류 자체의 취급·적재 특성(6.3)과는 별개로 관리한다.

| 배송 유형 | 식별자 | 제한 시간 | 시간 추가 보상 | 시간 초과 손실 |
|---|---|---|---|---|
| 일반 배송 | Normal | 없음 | 해당 없음 | 해당 없음 |
| 신속 배송 | Express | 있음(거리 기반, 7장). 생성 시점부터 감소 | 제한 시간 내 완료 시 지급 | 제한 시간 초과 후 완료 시 적용 |
| 신선 배송 | Fresh | 있음(신선도, 거리 기반, 7장). **상차 완료 시점부터** 감소 | 남은 신선도에 비례해 지급(신선도 보상, 11.1) | 해당 없음. 신선도가 0이 되면 폐기 물류로 전환되고 배송 실패(11.6) |

- 모든 유형에 기본 배송료와 거리 추가 배송료를 지급한다(배송 완료 시).
- 배송 유형은 확률 기반으로 무작위 배정하며, 정적·동적 생성 모두 동일한 확률을 적용한다.
- Express의 제한 시간 초과는 배송 실패가 아니다. Express의 배송 성공·실패는 영업 종료 시점까지 배송을 완료했는지로만 판정한다(11장).
- Fresh는 신선도가 0이 되는 순간 배송 실패가 확정된다(11.6). Fresh 도입은 2026-11-16 확정이다(`design/quick-specs/fresh-delivery-type-addition-2026-11-16.md`).

### 배송 유형 설정

배송 유형별로 다음 값을 설정 데이터에서 관리한다.

- 생성 확률
- 제한 시간 적용 여부(Normal 없음, Express 있음)
- 배송 제한 시간 계수
- 시간 초과 손실 계수
- 배송 실패 페널티 계수
- 기타 유형별 밸런싱 값

배송 유형 식별자와 수치 설정을 분리한다. 유형별 수치를 Enum에 직접 포함하지 않는다.

## 6.3. 물류 특징 (Cargo Traits)

물류 특징은 개별 물류의 취급 난이도와 차량 적재량에 영향을 주는 속성이다.

| 특징 | 식별자 | 효과 |
|---|---|---|
| 취급주의 | `Fragile` | 충돌 시 내구도가 일반 물류보다 크게 감소한다(감소 배율, 10.2). 초기 내구도는 일반 물류와 같다 |
| 고중량 | `Heavy` | 차량 무게 한도를 일반 물류보다 많이 사용한다 |
| 대형 | `Large` | 차량 적재 한도를 일반 물류보다 많이 사용한다 |

- 특징은 특징마다 독립된 확률로 추첨하며, 하나의 물류에 여러 특징이 함께 부여될 수 있다. 조합 제한은 두지 않는다.
- 적재 사용량은 일반 물류 기준값에 특징별 고정값을 더해 산정한다(예: Large는 적재 용량 사용량 가산, Heavy는 무게 적재량 가산).
- Heavy·Large의 사용량은 적재 가능 여부 판정(8.5)에만 쓰는 추상 수치이며, 실제 질량·부피·충돌 크기 등 물리 시뮬레이션에 반영하지 않는다.
- 특징이 많을수록 보상이 강화된다. 특징 1개당 고정 보상을 합산한다(11.1).
- 특징의 적재·내구도 효과와 보상 효과는 서로 다른 규칙으로 관리한다.

## 6.4. 내구도 (Durability)

모든 물류는 내구도 프로퍼티를 가진다. 취급주의(`Fragile`) 물류는 초기 내구도가 일반 물류와 같고, 충돌 시 감소 배율을 적용받아 더 크게 감소한다(10.2, 2026-11-16 확정).

내구도는 두 값으로 구분한다.

| 값 | 결정 시점 | 변화 |
|---|---|---|
| 초기 내구도 | 물류 생성 시점 | 고정. 이후 설정 변경의 영향을 받지 않는다 |
| 현재 내구도 | 초기 내구도에서 시작 | 차량 충돌로만 감소한다 |

초기 내구도는 다음과 같이 산정한다.

```
초기 내구도 = max(기준 내구도 − Σ 부여된 특징별 내구도 감산값, 1)
```

- `기준 내구도`: 일반 물류의 내구도(`CargoTraitConfig`)
- `특징별 내구도 감산값`: 부여된 특징마다 더해 빼는 값. 특징이 여러 개면 모두 합산한다
- 최소 1 보정: 현재 내구도가 0이 되면 폐기 물류로 전환되므로(11.6), 생성 즉시 폐기되는 물류를 만들지 않기 위해 유지한다(2026-11-16 확정)

현재 설정값(모두 `TODO(tuning)`, 16.4)은 다음과 같다.

| 물류 | 감산값 | 초기 내구도 |
|---|---|---|
| 일반 | — | 100 |
| Fragile | 0 (기존 50에서 변경, 2026-11-16) | 100 |
| Heavy | 0 | 100 |
| Large | 0 | 100 |

차량 충돌은 적재된 물류의 현재 내구도를 감소시킨다. 감소량 산식은 10.2를 따른다. 충돌이 보상에 미치는 영향은 내구도를 거쳐서만 발생한다.

현재 내구도가 0이 되면 그 물류는 폐기 물류로 전환된다(11.6). 0이 되기 전의 남은 내구도는 배송 보상에 반영하지 않는다. 내구도는 폐기 여부에만 영향을 준다(2026-11-16 확정).

**구현 현황 (2026-11-16):** 초기 내구도의 산정·보관은 구현되어 있다(`CargoTraitConfig.CreateSpec`, `Parcel.Cargo.Durability`). `CargoTraitConfig.asset`의 Fragile 감산값은 아직 50이며, 충돌 감소 구현 시 0으로 바꾸고 감소 배율을 추가한다. 현재 내구도, 충돌 감소, 폐기 전환, 피드백은 미구현이다.

# 7. 배송 제한 시간 시스템

## 7.1. 제한 시간 산정

배송 제한 시간은 신속 배송(Express)과 신선 배송(Fresh) 물류에 적용하며, 물류 생성 시점에 결정한다. Fresh의 제한 시간을 신선도라 부른다. 일반 배송(Normal) 물류에는 제한 시간이 없으므로 이 장의 산정·감소·초과 규칙을 적용하지 않는다.

Fresh의 신선도 계수 `M_fresh`는 Express 계수보다 작게 둔다(같은 거리에서 Express보다 짧다). 신선도는 생성 시 계산해 저장하며, 흐르기 시작하는 시점만 상차 완료 시점이다(7.2).

기본 산식은 다음과 같다.

`T_limit = T_base(D) * M_type + R`

| 변수 | 설명 |
|---|---|
| T_limit | 최종 배송 제한 시간 |
| T_base(D) | 배송 거리 기반 기본 제한 시간 |
| D | 물류센터와 배송지 사이의 거리 |
| M_type | 배송 유형별 제한 시간 계수 |
| R | 무작위 시간 편차 |

### 거리 계산

배송 거리는 물류센터와 배송지 사이의 직선거리를 기준으로 한다.

- Euclidean Distance 사용
- Unity 구현에서는 XZ 평면의 2D 거리를 사용
- 실제 주행 거리 및 도로 경로는 고려하지 않음

### 무작위 편차

배송 제한 시간에는 무작위 편차를 적용한다.

구체적인 최소·최대 편차와 분포 방식은 밸런싱 단계에서 결정한다.

## 7.2. 제한 시간 감소

- Express 물류는 생성되는 시점부터 배송 제한 시간이 감소한다.
- 플레이어가 물류를 확인하거나 상차하는 시점과 관계없이 시간이 흐른다.
- 상차 및 하차 중에도 제한 시간이 감소한다.
- 모든 Express 물류는 동일한 게임 시간 시스템을 기준으로 제한 시간을 관리한다.

동일 배송지 그룹의 물류는 같은 시간 시스템을 사용하므로 남은 제한 시간에 따른 상대적인 우선순위는 유지된다.

### Fresh 신선도 감소

- 물류센터에서 대기하는 동안에는 신선도가 줄지 않는다.
- 물류 1개의 상차가 완료된 순간부터 그 물류의 신선도가 줄어든다. 그룹으로 상차하면 물류마다 시작 시점이 다르다.
- 상차한 뒤에는 이동, 하차 진행, 처분 장소 체류 중에도 게임 시간 기준으로 계속 줄어든다.
- `남은 신선도 = T_fresh − (현재 게임 시각 − 상차 완료 시각)`

## 7.3. 제한 시간 초과

Express 물류가 배송 제한 시간을 초과하더라도 배송 자체가 실패하는 것은 아니다.

- 제한 시간 내 배송 완료: 기본 보상과 추가 보상 지급
- 제한 시간 초과 후 배송 완료: 기본 보상 지급, 시간 추가 보상 미지급, 시간 초과 손실 적용
- 하루 종료까지 미배송: 배송 실패 처리 및 배송 실패 페널티 적용

시간 초과 손실은 물류의 제한 시간이 최초로 초과되는 시점에 한 번만 적용한다.

시간이 계속 초과되어도 손실 금액이 누적되지는 않는다.

### 시간 초과 손실 산식

`L_late = L * M_late,type`

| 변수 | 설명 |
|---|---|
| L_late | 해당 물류의 시간 초과 손실 |
| L | 일반 물류 기준 시간 초과 손실 |
| M_late,type | 배송 유형별 시간 초과 손실 계수 |

시간 초과 손실과 배송 실패 페널티는 서로 다른 항목으로 관리한다.

### Fresh 신선도 소진

Fresh에는 위 시간 초과 규칙을 적용하지 않는다. 남은 신선도가 0이 되는 순간 폐기 물류로 전환되어 배송 실패가 확정된다(11.6). 시간 초과 손실은 적용하지 않는다. 하차 진행 중에 0이 되면 그 물류의 하차를 중단하고 진행도를 초기화한다.

## 7.4. 배송 우선순위

같은 배송지에 할당된 여러 물류는 다음 순서로 처리한다(2026-11-14 확정, 2026-11-16 Fresh 추가).

1. 상차된 Fresh 물류: 남은 신선도가 짧은 순서
2. Express 물류: 남은 배송 제한 시간이 짧은 순서
3. 물류센터에서 대기 중인 Fresh 물류: 신선도 총량이 짧은 순서
4. Normal 물류: 생성 순서(물류 식별자 오름차순)

같은 순위 안에서 값이 같으면 생성 순서로 정한다.

- 물류센터 UI의 그룹 내부 정렬과 그룹 상차에 동일한 순서 적용
- 배송지에서 그룹 하차 시 동일한 순서 적용
- 상단 나침반의 배송지 배치 순서에도 동일한 기준 적용(13장)

이 문서에서 "처리 순서"는 이 절의 순서를 뜻한다.

# 8. 물류센터 및 상차 시스템

## 8.1. 물류센터 UI

플레이어가 물류센터에 접근하여 상호작용 키를 일정 시간 유지하면 물류센터 UI를 표시한다.

UI를 여는 데 걸리는 시간은 물류센터 설정값이며 구체적인 값은 밸런싱 단계에서 결정한다.

UI에서는 배송지별 물류 그룹을 확인하고 상차할 물류를 선택할 수 있다.

### 그룹 정렬

배송지 그룹은 물류센터와 배송지 사이의 거리순으로 정렬한다.

모든 배송지 그룹은 목록에 표시한다. 해당 배송지에 미적재 물류가 없어도 그룹은 사라지지 않는다.

그룹에 속한 물류는 그룹 하위임을 알 수 있도록 왼쪽에 여백을 두고 표시한다.

### 그룹 내부 표시

각 물류의 배송 유형과 물류 특징을 표시한다.

Express 물류는 배송 제한 시간을 프로그레스 바로 표시한다. Normal 물류는 제한 시간 바를 표시하지 않는다.

그룹 내부 물류는 처리 순서(7.4)대로 정렬한다.

현재 차량에 적재된 물류 수량을 배송지별로 확인할 수 있으며, 차량의 적재 용량·무게 사용량을 함께 표시한다.

미적재 물류의 수량을 차량 적재량 정보와 혼합하여 표시하지 않는다.

## 8.2. 상차 선택 방식

플레이어는 다음 두 가지 방식으로 상차할 물류를 선택할 수 있다.

1. 개별 물류 선택
2. 배송지 그룹 전체 선택

그룹을 선택하면 해당 그룹에 속한 물류를 처리 순서(7.4)대로 상차한다.

물류를 선택하지 않고 상호작용 키를 유지하면 상차 대기열 선두 물류부터 상차한다.

선택한 그룹을 모두 상차하면 상차를 멈추고, 다른 그룹 물류를 자동으로 이어서 상차하지 않는다.

### UI 조작

물류센터 UI는 마우스로 조작한다. UI가 열려 있는 동안 커서가 표시된다.

물류 또는 배송지 그룹을 마우스로 누르고 있는 동안 상차가 진행된다. 물류 한 개당 소요시간이 필요하며, 그룹을 누르고 있으면 그룹 내 물류를 처리 순서(7.4)대로 이어서 상차한다.

상차 진행도는 현재 물류 하나의 진행 바로 표시하고, 상차가 완료된 물류의 행은 목록에서 하나씩 사라진다. 배송지 그룹의 미적재 수량과 적재 수량은 완료 즉시 갱신되며, 그룹 머리글은 물류가 모두 실린 뒤에도 `x0` 상태로 목록에 남는다.

Express 물류의 배송 제한 시간은 생성 시점에 확정된 만료 시각을 게임 시계 기준(`HH:mm`)으로 표시한다. 제한 시간 프로그레스 바는 남은 제한 시간의 비율을 실시간으로 보여 준다. Normal 물류는 만료 시각 자리에 `--:--`를 표시하고 바를 숨기며, 행의 위치와 크기는 Express 물류와 같다.

누르고 있던 마우스를 놓거나 커서가 해당 행을 벗어나면 진행 중인 물류의 상차 진행도를 초기화한다. 이미 상차가 완료된 물류는 차량에 유지한다.

고른 물류를 모두 상차하면 마우스를 계속 누르고 있더라도 해당 상호작용을 종료한다.

상차가 진행되는 동안에도 UI는 닫히지 않는다. 플레이어가 닫기 버튼을 누르면 UI가 닫히고 진행 중인 상차는 취소된다.

## 8.3. 상차 진행

- 상차할 물류를 선택한 뒤 상호작용 키를 누르고 있으면 상차가 진행된다.
- 물류 한 개당 설정된 상차 소요시간이 필요하다.
- 현재 상차 중인 물류 하나의 진행 UI를 표시한다.
- 상차가 완료되면 다음 물류로 넘어간다.
- 전체 그룹 작업시간을 하나의 긴 프로그레스 바로 표현하지 않는다.

상차 소요시간은 물류별 N초이며 구체적인 값은 밸런싱 단계에서 결정한다.

## 8.4. 상차 중단

상차 중 상호작용 키를 놓으면 현재 진행 중인 물류의 상차 진행도를 초기화한다.

- 이미 상차 완료된 물류: 차량에 유지
- 현재 상차 중인 물류: 진행도 초기화
- 아직 상차를 시작하지 않은 물류: 물류센터에 유지

이후 다시 상차를 시작하면 미완료 물류부터 진행한다.

## 8.5. 적재 한도

차량은 서로 독립적인 두 가지 한도를 가진다.

| 한도 | 식별자 | 판정 대상 | 초과 가능 여부 |
|---|---|---|---|
| 적재 한도 | Cargo Capacity | 물류의 적재 용량 사용량 합계 | 불가 |
| 무게 한도 | Weight Capacity | 물류의 무게 적재량 합계 | 초과 상한 `W_max`까지 가능 (8.6) |

물류를 상차하려면 다음 두 조건을 모두 만족해야 한다. 하나라도 만족하지 못하면 해당 물류를 상차할 수 없다.

1. 상차 후 총 적재 용량 사용량 ≤ 적재 한도
2. 상차 후 총 무게 적재량 ≤ 초과 상한 `W_max` (= 무게 한도 × 최대 초과 배율, 8.6)

- 일반 물류는 기본 사용량을, 대형(`Large`)은 더 많은 적재 용량을, 고중량(`Heavy`)은 더 많은 무게를 사용한다(6.3).
- 사용량은 적재 가능 여부를 판정하는 추상 수치이며 물리 시뮬레이션에 반영하지 않는다.
- 그룹·선택 상차 도중 처리 순서상 다음 물류가 적재 한도를 넘거나, 상차 후 무게가 무게 한도(`W`)를 넘으면 그 물류에서 상차를 자동 종료한다. 뒤의 더 작은 물류로 건너뛰지 않는다(2026-11-14 확정, 무게 기준 2026-11-16 확정). 무게 한도 초과 적재는 개별 상차로만 할 수 있다(8.6).
- 상차 UI에서는 현재 사용량으로 실을 수 없는 물류(적재 한도 초과 또는 `W_max` 초과)를 행 단위로 비활성 표시한다.
- 상차 불가 안내는 적재 한도 초과와 무게 초과 상한 초과를 구분해 표시한다.
- 적재하지 못한 나머지 물류는 물류센터에 남는다.
- 하차하면 해당 물류의 사용량만큼 차량의 사용량이 줄어든다.

## 8.6. 무게 한도 초과 적재 (2026-11-16 확정)

무게 한도(`W`)는 넘을 수 있는 기준선이며, 넘은 무게만큼 차량이 느려진다. 실제로 넘을 수 없는 상한은 초과 상한 `W_max`다. 적재 한도는 초과할 수 없다.

### 상차

- 개별 상차: 상차 후 무게가 `W_max` 이하이면 `W`를 넘어도 상차할 수 있다.
- 그룹·선택 상차: 상차 후 무게가 `W`를 넘는 물류에서 자동 종료한다(8.5). 연속 상차로 실수로 과적되는 것을 막기 위함이다.
- `W_max`를 넘게 되는 물류는 어떤 방식으로도 상차할 수 없다.

### 속도 감소 산식

```
W_max = W × r_max
m = max(m_min, 1 − k × max(0, w − W) / W)
```

| 변수 | 의미 | 초기값 | 안전 범위 |
|---|---|---|---|
| w | 현재 총 무게 적재량 | — | 0 ~ W_max |
| W | 무게 한도 (`VehicleCargoConfig`) | 6 | ≥ 1 |
| r_max | 최대 초과 배율 | 1.5 | 1.0 ~ 2.0 (1.0이면 초과 적재 없음) |
| k | 속도 감소 계수 | 1.0 | 0.5 ~ 2.0 |
| m_min | 최소 속도 배율 | 0.5 | 0.3 ~ 0.9 |
| m | 속도 배율 | — | m_min ~ 1 |

- 예시: `W` = 6, `w` = 8 → `m` = 1 − 1.0 × 2/6 ≈ 0.67 (최고 속도·가속도 33% 감소).
- 초기값에서 `w` = `W_max` = 9이면 `m` = 0.5로 하한과 같다.
- `w` ≤ `W`이면 `m` = 1이며 아무 영향이 없다.

### 적용

- 일반·고속 두 주행 모드의 전진 최고 속도와 가속도에 `m`을 곱한다(모드 전환 보간 후 값에 적용).
- 후진 최고 속도, 제동·관성 감속, 회전, 드리프트 값은 바꾸지 않는다.
- `m`은 상차·하차·처분이 완료될 때마다 다시 계산한다. 폐기 물류는 처분할 때까지 무게에 포함된다(11.6).
- 초과 적재는 보상, 내구도, 별점에 영향을 주지 않는다. 대가는 느려진 이동뿐이다.

### 예외

- 물류 하나의 무게 적재량이 `W_max`보다 크면 영원히 상차할 수 없다. 물류 특징 설정(Heavy 무게 가산)은 단일 물류 최대 무게가 `W_max` 이하가 되도록 정하며, 설정 검증에서 확인한다.
- 이미 실은 상태에서 설정값이 바뀌어 `w` > `W_max`가 되어도 물류를 내리지 않는다. 산식대로 `m_min`이 적용되고 추가 상차만 막힌다.

## 8.7. 상차 비용

현재 마일스톤에서는 상차 비용을 부과하지 않는다.

개별 상차, 그룹 상차, 물류센터 재방문 상차 모두 무료이다.

# 9. 운송 및 배송 시스템

## 9.1. 배송 경로

플레이어는 정해진 배송 순서 없이 배송지를 자유롭게 방문할 수 있다.

- 배송 순서는 플레이어가 직접 결정한다.
- 여러 배송지를 원하는 순서로 방문할 수 있다.
- 배송 도중 물류센터에 재방문하여 추가 물류를 상차할 수 있다.
- 배송 제한 시간과 차량의 적재 한도·무게 한도를 고려하여 배송 계획을 수립한다.

현재 마일스톤에서는 지도 및 미니맵 기능을 후순위로 둔다.

맵의 규모가 크지 않고 별도 개발 비용이 발생하기 때문에 현재 핵심 기능으로 구현하지 않는다.

## 9.2. 배송지 도착 및 하차

플레이어가 배송지에 접근하여 상호작용 키로 상호작용하면 해당 배송지에 배송할 물류를 하차할 수 있다.

- 차량에 해당 배송지로 배송할 물류가 하나 이상 있어야 한다.
- 배송할 물류가 없다면 상호작용할 수 없다.
- 물류 한 개당 설정된 하차 소요시간이 필요하다.
- 상호작용 키를 누르고 있는 동안 하차가 진행된다.

하차 소요시간은 물류별 N초이며 구체적인 값은 밸런싱 단계에서 결정한다.

## 9.3. 하차 우선순위

동일 배송지에 할당된 여러 물류는 처리 순서(7.4)대로 하차한다.

## 9.4. 하차 중단

하차 중 상호작용 키를 놓으면 현재 진행 중인 물류의 하차 진행도를 초기화한다.

- 이미 하차 완료된 물류: 배송 완료 상태 유지
- 현재 하차 중인 물류: 진행도 초기화
- 아직 하차를 시작하지 않은 물류: 차량에 유지

배송 완료 판정은 개별 물류의 실제 하차 완료 시점에 이루어진다.

# 10. 차량 및 환경 시스템

## 10.1. 플레이어 차량

현재 마일스톤에서는 단일 플레이어블 차량을 사용한다.

- 차량 종류: 1종
- 차량 성능: 주행 모드에 따라 달라짐(10.4)
- 적재 한도·무게 한도: 고정(8.5). 주행 성능 설정과 분리된 차량 적재 설정 데이터로 관리한다(14.2)

차량 성능 업그레이드 및 차량 종류별 성능 차이는 현재 마일스톤에서 구현하지 않는다.

## 10.2. 충돌 처리

차량 충돌은 물리적 방해 요소로 작동하며, 적재된 물류의 내구도를 감소시킨다(6.4).

충돌로 인해 다음과 같은 직접 페널티는 발생하지 않는다.

- 별도의 속도 저하 디버프
- 배송 보상 직접 감소
- 경제적 페널티

충돌의 결과는 물류 내구도로만 나타나며, 보상에는 폐기 여부(11.6)를 통해서만 영향을 준다.

### 충돌 내구도 감소 (2026-11-16 확정)

충돌 세기는 충돌로 내 차량이 받은 속도 변화량으로 판정한다. 벽·NPC·다른 차량 등 상대와 무관하게 같은 기준을 적용하며, 질량 차이(체급)가 결과에 자연히 반영된다. 상세 근거는 `collision-durability-rules.md`에서 관리한다.

```
Δv = 충돌 직전과 판정 창(0.06초) 뒤 내 차량 수평 속도의 차이   (= 충격량 크기 ÷ 내 차량 질량)
damage = min((Δv − ImpactThreshold) × DamagePerVelocity, MaxDamagePerImpact)   (Δv < ImpactThreshold이면 0)
물류별 감소량 = damage × M_trait
```

| 변수 | 설명 | 초기값 (`TODO(tuning)`) |
|---|---|---|
| ImpactThreshold | 감소가 시작되는 속도 변화량 하한선 | 1.5 m/s |
| DamagePerVelocity | 하한선을 넘은 속도 변화량 1 m/s당 감소량 | 12 |
| MaxDamagePerImpact | 충돌 1회 기본 감소량 상한 | 60 |
| ImpactCooldown | 감소 후 추가 감소를 막는 시간 | 0.5초 |
| M_trait | 물류 특징 감소 배율. Fragile이면 적용, 그 밖은 1 | Fragile 1.5 |

- 적재된 모든 물류에 같은 `damage`를 기준으로 감소시키고, 물류마다 `M_trait`만 곱한다. 특징이 여럿이어도 Fragile 배율만 적용한다.
- 충돌 시작 직후의 짧은 판정 창(0.06초) 안의 충격만 합산해 한 번 판정한다. 그 뒤로 접촉이 유지되는 동안(밀어붙이기)은 감소시키지 않는다(`collision-durability-rules.md` 3장).
- 지면 접촉과 착지 충격은 제외한다(접촉 법선이 지면 판정 기준 이상인 접촉).
- 충돌 외의 내구도 감소 사건은 없다. 월드 오브젝트의 효과(10.3)도 내구도를 감소시키지 않는다.
- 충돌면 물리 재질의 반발 계수 기준은 0이다. 반발이 있는 재질을 쓸 때는 감소량을 다시 검증한다.

현재 차량 기준(고속 최고 속도 5 m/s, 일반 3 m/s, 반발 0) 검산:

| 상황 | 일반 물류 | Fragile |
|---|---|---|
| 고속 최고 속도 벽 정면 충돌 (Δv ≈ 5) | −42 | −63 |
| 일반 최고 속도 벽 정면 충돌 (Δv ≈ 3) | −18 | −27 |
| 폐기까지 고속 정면 충돌 횟수 (초기 100) | 3회 | 2회 |

물류 내구도 감소는 플레이어 차량의 충돌 판정에서만 결정한다. 월드 오브젝트(10.3)는 내구도에 관여하지 않는다.

위 "직접 페널티 없음"은 충돌 자체에 대한 규칙이다. 월드 오브젝트가 가진 효과(최고 속도 영향, 진행 방향 변경 등)는 충돌 페널티가 아니라 오브젝트 고유의 주행 방해 효과이며, 10.3의 규칙을 따른다.

### 이동 및 충돌 구현 기준

차량은 물리 바디를 사용하되, 지면 판정과 서스펜션은 바퀴 4점의 스피어캐스트로 처리하고 구동·조향·횡방향 접지는 힘으로 인가한다. 지면은 별도 레이어(`Drivable`)로 판정한다.

맵 충돌은 렌더링 메시와 분리한다(2026-11-16 확정, 16.7). 접지면은 평면 BoxCollider로, 벽·연석·난간은 타일 충돌 메시를 하나로 합친 베이크 메시로 구성하여 타일 이음매의 물리 충격을 막는다. 베이크는 에디터 도구로 수행하며, 맵 타일을 수정하면 다시 베이크한다. 경사·다리 타일은 배치 시점에 기울어진 접지 콜라이더를 생성하도록 도구를 확장한다. 맵 렌더링은 정적 배칭을 1순위 최적화로 적용한다.

## 10.3. 환경 장애물

주행을 방해하는 월드 오브젝트는 정적 오브젝트와 동적 오브젝트(NPC) 두 계열로 나눈다. 공통 구조와 원칙은 `design/quick-specs/world-obstacle-objects-framework-2026-11-16.md`를 따른다.

- 정적 오브젝트: 스스로 이동하지 않는 3D 모델 리소스(라바콘, 표지판 등). 효과가 없을 수도 있고, 트리거·효과·수명 컴포넌트를 조합해 효과를 가질 수도 있다(상호작용 장애물 포함).
- 동적 오브젝트(NPC): 보행자, 도로 주행 차량. 효과를 두지 않으며, 물리 판정을 받는 능동적 방해 요소로 둔다.
- 두 계열 모두 물류 내구도에 직접 관여하지 않는다(10.2).
- 오브젝트별 효과·수치·배치는 모델 리소스 전수조사 후 오브젝트 단위로 기획한다(미정).
- 장애물은 맵 제작 단계에서 고정 배치한다.
- 매 플레이마다 동일한 위치에 배치한다. NPC의 시작 위치와 이동 경로도 맵 제작 단계에서 정한다.

### 레벨 배치 규칙 (2026-11-16 확정, 16.5)

맵 구조 때문에 진행할 수 없는 상황을 배치 단계에서 막는다.

- 물류센터, 모든 배송지, 처분 장소는 도로로 서로 연결되어 있고, 각 상호작용 지점은 도로에서 접근할 수 있다.
- 고정 오브젝트는 도로를 완전히 막지 않는다. 상호작용으로 열 수 있는 막힌 길은 예외이며, 이 경우에도 우회로를 둔다.
- NPC 이동 경로가 상호작용 지점 진입을 계속 막지 않게 한다.
- 이 규칙으로도 생기는 예외 상황은 차량 복구(10.6)로 해소한다.

배송지도 맵 제작 단계에서 고정 배치한다.

따라서 장애물과 배송지는 게임 시작 시 무작위 생성하거나 배치하지 않는다.

### 맵 구성 및 축척

1차 맵은 3×3 블록 도로 루프에 배송지 5곳과 물류센터 1곳을 배치하고, 장애물과 가로 시설물을 같은 블록 안에 고정 배치한다.

축척 기준은 도로 1칸 3m(2차선), 플레이어 차량 폭 0.38m·길이 0.81m이다. 맵 제작 도구(맵 페인터)의 기본 칸 크기도 3m를 사용한다.

## 10.4. 주행 모드와 드리프트

### 주행 모드

플레이어는 ctrl 키로 주행 모드를 전환한다.

| 모드 | 용도 | 성능 |
|---|---|---|
| 일반 | 도시 주행, 좁은 구간에서의 정밀한 조작 | 기준 성능 |
| 고속 | 배송 제한 시간 대응, 추격자 회피(후속) | 높은 최고 속도, 낮은 회전 성능·접지력 |

- 두 모드의 차이는 최고 속도, 가속도, 최대 회전 속도, 접지력, 조향 반응 속도로 구성한다.
- 모드 전환 시 성능 값은 설정된 전환 시간에 걸쳐 보간한다. 회전 성능이 계단처럼 튀지 않게 하기 위함이다.
- 전환은 접지 상태이며 상호작용 중이 아닐 때만 허용한다.
- 고속 모드는 사용 시간 게이지를 소모하고, 모드 전환에는 쿨다운이 있다(`design/quick-specs/fast-mode-gauge-speedometer-2026-11-17.md`). 연료·내구도 비용은 두지 않는다.
- 고속 모드는 같은 속도에서의 최소 회전 반경이 일반 모드보다 항상 크다. 따라서 좁은 구간에서는 감속만으로 해결되지 않고 모드 전환이 필요하다.
- 고속 모드에서 일반 모드로 전환해도 관성은 유지되며, 최고 속도에 가속도 기준으로 자연 감속한다.
- 현재 주행 모드는 HUD에 표시한다.

### 드리프트

- shift 키를 누르고 있는 동안 드리프트가 발생한다.
- 접지 상태이고 전진 속도가 설정값 이상일 때만 발동한다.
- 드리프트 중에는 접지력이 크게 낮아지고 최대 회전 속도가 높아진다.
- 별도의 속도 감소 로직을 두지 않는다. 옆방향 미끄러짐이 감쇠되는 과정에서 속도가 자연히 줄어든다.
- 키를 놓으면 접지력이 즉시 원래 값으로 돌아온다.
- 드리프트는 배송 제한 시간, 충돌 규칙, 보상에 영향을 주지 않는다.

주행 모드와 드리프트에 관련된 구체적인 수치는 밸런싱 단계에서 결정한다(16.4).

## 10.5. 카메라

플레이어 차량을 뒤에서 따라가는 3인칭 추적 카메라를 사용한다.

- 카메라와 차량 사이에 벽·건물 등의 장애물이 있으면 카메라를 차량 쪽으로 당겨 벽을 뚫지 않는다.
- 카메라를 당길 때 높이는 유지하고, 차량에 지나치게 붙지 않도록 최소 거리를 둔다.
- 장애물에 닿을 때 화면이 순간적으로 확대되는 연출은 사용하지 않는다.
- 목적지 방향은 화면 상단 나침반(13장)으로 보조한다.

## 10.6. 차량 복구 (2026-11-16 확정, 16.5)

차량이 장애물 사이에 끼거나 뒤집혀 정상 주행이 불가능할 때, 플레이어가 직접 복구한다. 기울어진 차량을 토크로 다시 세우는 자동 수평 유지(`KeepUpright`)는 그대로 유지하며, 복구는 이것으로 해결되지 않는 상황을 위한 수단이다.

### 복구 실행

- 리셋 키(R)를 복구 홀드 시간 동안 누르고 있으면 복구한다. 누르는 동안 진행도를 표시하고, 도중에 떼면 취소된다.
- 하루 운영 중 조작 가능한 상태에서만 사용할 수 있다. 하루 종료로 조작이 잠긴 뒤에는 사용할 수 없다.
- 상·하차 작업 중에 복구하면 작업이 중단되고 현재 물류의 진행도가 초기화된다(16.2-3과 같은 규칙).

### 안전 지점

- 주행 중 기록 간격마다 현재 위치를 검사하고, 아래 조건을 모두 만족하면 위치와 진행 방향을 안전 지점으로 기록한다.
  - 바퀴 4개가 모두 `Drivable` 지면에 닿아 있다.
  - 차체 기울기가 기준 이하다.
  - 다른 콜라이더와 겹치지 않는다.
- 최근 안전 지점 여러 개를 보관한다(보관 개수는 설정값).

### 복구 위치

1. 기록된 지 최소 경과 시간 이상 지난 안전 지점 중 가장 최근 지점을 쓴다. 방금 끼인 자리로 다시 돌아가지 않기 위해서다.
2. 그 지점이 다른 물체와 겹치면 그보다 이전 지점을 쓴다.
3. 쓸 수 있는 지점이 없으면 물류센터 앞 지정 위치로 옮긴다.

복구 시 차량을 수평으로 세우고 기록된 진행 방향을 보게 하며, 속도와 회전 속도를 0으로 만든다.

### 대가와 영향

- 복구 후 조작 잠금 시간 동안 차량을 조작할 수 없다. 게임 시간과 물류 제한 시간은 계속 흐른다.
- 적재 물류는 그대로 유지된다. 복구 이동은 충돌이 아니므로 내구도가 변하지 않는다(10.2).
- 금액 비용은 없다.

# 11. 보상 및 경제 시스템

## 11.1. 기본 보상 구조

배송 보상은 기본 배송료, 거리 추가 배송료, 시간 추가 보상, 신선도 보상, 물류 특징 보상으로 구성한다.

| 보상 요소 | 적용 조건 |
|---|---|
| 기본 배송료 | 배송 완료 |
| 거리 추가 배송료 | 배송 완료 (물류센터~배송지 직선거리에 비례) |
| 시간 추가 보상 | Express를 제한 시간 내 배송 완료 |
| 신선도 보상 | Fresh를 폐기 전에 배송 완료 (남은 신선도에 비례) |
| 물류 특징 보상 | 특징이 부여된 물류를 배송 완료 (특징 1개당 고정 보상 합산) |

### 기본 배송료

- 모든 정상 배송에 적용한다.
- 물류별 기본 배송료를 지급한다.
- 보상 최저 하한으로 작동한다.

### 거리 추가 배송료

- 물류센터와 배송지 사이의 거리를 기준으로 산정한다.
- 실제 주행 거리가 아닌 직선거리를 기준으로 한다.

### 시간 추가 보상

- Express 물류를 배송 제한 시간 내에 배송 완료하면 지급한다.
- Express 물류를 제한 시간 초과 후 배송 완료하면 지급하지 않는다.
- Normal 물류는 제한 시간이 없으므로 시간 추가 보상 판정을 적용하지 않는다.
- Fresh 물류는 시간 추가 보상 대신 신선도 보상을 받는다.

### 신선도 보상 (2026-11-16 확정)

`B_fresh_earned = B_fresh * clamp(T_remain / T_fresh, 0, 1)`

| 변수 | 설명 |
|---|---|
| B_fresh_earned | 실제 지급하는 신선도 보상 |
| B_fresh | Fresh 최대 신선도 보상. Express 시간 추가 보상보다 크게 둔다 |
| T_remain | 하차를 완료한 순간의 남은 신선도 |
| T_fresh | 그 물류의 신선도 총량 |

- 감소 형태는 선형이다. 예: `B_fresh` 200, 신선도 120초 중 90초가 남았을 때 배송하면 200 × 0.75 = 150이다.
- 신선도 보상은 하차 완료 시점에 계산한다. 보상 관련 값을 생성 시점에 고정하는 원칙(14.2)의 예외이며, `B_fresh`와 `T_fresh`는 생성 시점 값을 쓴다.

### 물류 특징 보상

- 특징이 부여된 물류를 배송 완료하면 지급한다.
- 특징 1개당 특징별 고정 보상을 더하므로, 특징이 많을수록 보상이 커진다.
- 배송 유형의 시간 보상 조건과 별개로 적용한다. 미배송 물류에는 지급하지 않는다.

각 보상의 구체적인 금액 및 산식은 밸런싱 단계에서 결정한다.

## 11.2. 배송 완료 (Normal, Express 제한 시간 내)

Normal 물류를 배송 완료하면 기본 배송료, 거리 추가 배송료, 물류 특징 보상을 지급한다.

Express 물류를 제한 시간 내 배송 완료하면 여기에 시간 추가 보상을 더해 지급한다.

Fresh 물류를 폐기 전에 배송 완료하면 여기에 신선도 보상을 더해 지급한다.

거리 추가 배송료는 배송을 완료하면 지급한다(2026-11-11 확정, 16.1-5).

## 11.3. Express 제한 시간 초과 후 배송 완료

Express 물류가 배송 제한 시간을 초과한 뒤에도 배송을 완료하면 다음 규칙을 적용한다.

- 기본 배송료, 거리 추가 배송료, 물류 특징 보상 지급
- 시간 추가 보상 미지급
- 시간 초과 손실 적용
- 배송 자체는 성공으로 판정

## 11.4. 하루 종료 시 미배송

영업 종료 시각까지 배송을 완료하지 못한 물류는 배송 실패 처리한다.

- 기본 배송료 미지급
- 거리 추가 배송료, 시간 추가 보상, 물류 특징 보상 미지급
- 배송 실패 페널티 적용
- 미배송 물류 폐기

배송 실패 페널티는 일반 물류의 기준 손실값을 바탕으로 배송 유형별 계수를 적용한다.

`P_failure = P * M_type`

| 변수 | 설명 |
|---|---|
| P_failure | 최종 배송 실패 페널티 |
| P | 일반 물류 기준 배송 실패 손실 |
| M_type | 배송 유형별 실패 페널티 계수 |

## 11.5. 경제 시스템 범위

현재 마일스톤에서는 수익 사용처를 구현하지 않는다.

차량 및 물류센터 업그레이드, 성능 개선 등 성장 시스템은 후속 마일스톤에서 다룬다.

## 11.6. 폐기 물류 (공통 규칙)

**확정(2026-11-16).** 물류가 더 이상 배송할 수 없는 상태가 되면 폐기 물류(`Spoiled`)로 전환한다. 원인과 무관하게 아래 규칙을 공통으로 적용한다.

| 원인 | 상태 |
|---|---|
| 현재 내구도가 0이 됨(6.4) | 확정 |
| 신선도가 0이 됨(Fresh 배송 유형, 7.3) | 확정 (2026-11-16) |

1. 폐기로 전환되는 순간 배송 실패가 확정되고, 배송 실패 페널티 `P * M_type`(11.4)을 매긴다. 정산에는 실패 항목으로 집계한다.
2. 시간 초과 손실은 적용하지 않는다(16.1-4 "중복 적용 없음"과 같은 원칙).
3. 폐기로 전환되면 그 물류의 목적지가 원래 배송지에서 처분 장소로 재설정된다(2026-11-16 수정).
   - 원래 배송지의 하차 대상, 배송지 물류 아이콘, 나침반 목표에서는 빠진다.
   - 상차 UI·적재 UI에서는 처분 장소 그룹으로 묶여 표시된다.
   - 처분 장소의 물류 아이콘과 나침반 화살표가 폐기 물류의 목적지로 표시된다. 나침반에서는 배송지 화살표 다음에 배치한다(제안, 구현 시 확인).
   - 처분 장소는 배송지 할당(5장)과 일일 할당 한도의 대상이 아니다. 재설정은 할당 한도를 소모하지 않는다.
4. 폐기 물류는 처분하기 전까지 적재 한도와 무게 한도를 그대로 차지한다.
5. 하차 진행 중에 폐기로 전환되면 그 물류의 하차를 중단하고 진행도를 초기화한다.
6. 영업 종료 시 이미 폐기된 물류에는 페널티를 다시 매기지 않는다. 차량에 남은 폐기 물류는 정리한다.

### 처분 장소 (Disposal Site)

- 폐기 물류의 목적지다(규칙 3). 상호작용 키를 누르고 있으면 차량에 실린 폐기 물류를 1개씩 처분한다. 배송지의 하차와 같은 방식이며, 물류 1개마다 처분 소요시간(설정값)이 걸린다.
- 처분된 물류는 차량에서 빠지고, 적재 한도와 무게 한도가 회복된다.
- 처분에는 보상도 비용도 없다. 리스크는 이동 시간과 적재 공간 손실이다.
- 폐기 물류가 없으면 처분 작업을 할 수 없다. 상호작용 키를 누르면 "처분할 물류 없음"을 표시한다.
- 처분 장소는 맵 제작 단계에서 고정 배치한다. 위치와 개수는 레벨 디자인에서 정한다(제안: 1차 맵에 1곳, 물류센터에서 떨어진 곳).

# 12. 일일 정산 시스템

## 12.1. 정산 진입

다음 중 하나가 발생하면 하루 운영을 종료하고 일일 정산 화면으로 전환한다.

- 영업 종료 시각 도달
- 모든 배송 완료에 따른 조기 종료

영업 종료 시 미배송 물류는 일괄 배송 실패 처리한다.

## 12.2. 정산 화면 구성

정산 화면은 요약과 상세 내역을 하나의 화면에 통합한다.

### 상단 요약

- 일일 별점(12.4)과 조건부 성공 건수(`성공 S / 발생 N`)
- 최종 정산 금액
- 배송 완료 건수
- 미배송 건수
- 미배송 페널티

### 하단 상세 내역

- 기본 배송료 합계
- 거리 추가 배송료 합계
- 시간 추가 보상 획득액
- 신선도 보상 합계
- 시간 추가 보상 미지급액
- 물류 특징 보상 합계
- 시간 초과 손실
- 미배송 페널티

화면에는 해당 하루의 총 수익과 손실을 이해할 수 있도록 항목별 합계를 표시한다.

정산 이후 메인 화면으로 이동한다.

## 12.3. 정산 계산

기본적인 정산 구조는 다음과 같다.

`FinalSettlement = DeliveryIncome - DeliveryFailurePenalty - LateDeliveryLoss`

여기서 `DeliveryIncome`은 실제 지급 대상이 되는 배송 보상의 합계이다.

거리 추가 배송료는 배송 완료 시 지급하며, 미배송 페널티와 시간 초과 손실은 중복 적용하지 않는다. 최종 정산 금액은 음수를 허용하고 하한을 두지 않는다(2026-11-11 확정, 16.1-4~6).

## 12.4. 일일 별점

**확정(2026-11-16).** 하루 결과를 별 0~3개로 피드백한다. 판정 근거는 발생한 물류 대비 조건부 성공 비율이다.

### 정의

| 변수 | 설명 |
|---|---|
| N | 발생 물류 수. 하루 동안 생성된 전체 물류(정적 + 동적) |
| S | 조건부 성공 수. 영업 종료 전에 배송을 완료하고 배송 유형의 조건까지 충족한 물류 |
| R | 조건부 성공 비율. `R = S / N` |
| T2, T1 | 별 2개·1개 경계값(설정 데이터) |

배송 유형별 성공 조건은 다음과 같다.

| 배송 유형 | 성공 조건 |
|---|---|
| Normal | 배송 완료 |
| Express | 제한 시간 내 배송 완료. 초과 후 완료는 배송 자체는 성공(11.3)이지만 별점상 실패다 |
| Fresh | 폐기 전 배송 완료(신선도가 남아 있을 때). 남은 양은 보상으로만 차등 |
| 공통 | 폐기 물류(11.6)는 실패다 |

새 배송 유형을 도입하면 그 유형의 성공 조건을 이 표에 추가한다.

### 판정 순서

1. `N = 0`이면 별점을 표시하지 않고 "판정할 물류 없음"을 표시한다.
2. 최종 정산 금액(12.3)이 0 미만이면 별 0개다. 정산 금액이 정확히 0이면 이 조건에 해당하지 않는다.
3. 그 밖에는 `R`로 판정한다.

| 별 | 조건 |
|---|---|
| 3개 | `R = 1` (모든 물류가 조건을 충족해 배송 완료. 고정) |
| 2개 | `R ≥ T2` (초기값 0.7) |
| 1개 | `R ≥ T1` (초기값 0.4) |
| 0개 | `R < T1` |

`T2`와 `T1`은 설정 데이터에 두고 `TODO(tuning)`으로 관리한다(16.4). `0 < T1 < T2 < 1`을 지킨다.

예시: 하루 물류 10개 중 Express 제한 시간 초과 완료 1개, 미배송 1개, 나머지 8개 조건 충족이면 `R = 8 / 10 = 0.8`이므로 정산이 0 이상일 때 별 2개다.

물류센터 UI에서는 배송지별 물류 그룹을 거리순으로 정렬한다.

물류센터 UI의 무게 사용량은 무게 한도(`W`)를 넘으면 경고색으로 표시한다. 상차하면 `W`를 넘게 되는 물류 행에는 경고 표시를 하되 상차는 허용하고, `W_max`를 넘게 되는 행은 비활성으로 두고 `무게 초과`를 표시한다(8.6).

Express 물류의 배송 제한 시간은 프로그레스 바로 표시한다. Normal 물류는 `--:--`로 표시한다.

적재 물류 패널에서도 제한 시간이 있는 물류(Express, Fresh)는 행 아래에 남은 제한 시간 바를 표시하고, Normal 행에는 바가 없다. Express가 제한 시간을 넘으면 바를 비우고 `#지연` 태그를 붙인다(2026-11-17 확정).

유형은 색만으로 구분하지 않는다. 적재 물류 행에 Express는 `#특급`, Fresh는 `#신선` 유형 태그를 붙인다(2026-11-17 확정, 색약 대체). 물류센터에서는 신선도 총량(예: `↻2:00`)을 표시하고 바를 가득 찬 상태로 고정한다. 상차 후에는 배송지 물류 아이콘과 적재 물류 UI에서 신선도 바가 줄어든다.

미니맵은 현재 마일스톤에서 구현하지 않는다. 대신 적재 물류 패널에 방향 화살표를 표시한다(2026-11-17 확정, 상단 나침반 패널을 대체). 패널 맨 위에 `물류센터` 고정 행과 파란 화살표를 항상 표시하고(적재 물류가 없어도 이 행은 보인다), 배송지 그룹과 처분 장소 그룹의 헤더마다 가장 왼쪽에 그 목적지를 가리키는 화살표를 둔다. 화살표는 차량 전방을 위로 하여 목적지 방향으로 회전한다. 그룹 순서는 적재 물류 패널의 기존 순서를 따른다.

HUD 화면 영역 배치는 `design/quick-specs/hud-layout-2026-11-17.md`를 따른다.

화면에 표시하는 문구는 한국어로 통일한다(2026-11-17 확정). 숫자·단위(`km/h`, `₩`)와 키 이름은 예외다.

# 16. 미결정 사항 및 추가 검토 사항

아래 항목은 현재 논의에서 구체적으로 확정되지 않은 사항이다. 임의의 값이나 규칙을 적용하지 않고 별도 관리한다.

## 16.1. 우선 확정이 필요한 정책

### 1. 모든 배송 완료의 정확한 판정 기준

하루 조기 종료 조건은 모든 배송 완료로 확정되었다.

다만 다음 상황의 정확한 처리 기준은 추가 확인이 필요하다.

- 현재 생성된 물류를 모두 배송했지만, 앞으로 생성될 동적 물류가 남아 있는 경우
- 동적 물류 생성 시스템이 종료되었고 현재 존재하는 물류를 모두 배송한 경우
- 동적 물류 생성 가능량을 모두 소진했지만 아직 예정된 생성 시점이 남아 있는 경우

조기 종료를 판정할 때 '모든 배송'이 현재 생성된 물류 전체를 의미하는지, 하루 동안 생성될 예정인 물류까지 포함하는지 정의해야 한다.

**확정(2026-11-11):** 동적 물류 생성이 끝난 상태(생성 마감 도달·생성 가능량 소진·할당 가능 배송지 없음)에서 배송되지 않은 물류가 하나도 없을 때만 조기 종료한다. 앞으로 생성될 동적 물류가 남아 있으면 영업을 계속한다.

### 2. 정적 물류 생성량이 배송지 할당 가능량을 초과하는 경우

**확정(2026-11-11):** 정적 물류 생성량을 배송지 전체 잔여 할당량으로 제한한다(4.1에 반영). 무작위로 결정한 생성량이 잔여 할당량보다 크면 잔여 할당량만큼만 생성하며, 생성한 물류를 폐기하지 않는다.

### 3. 동적 물류 생성 실패 시 생성 가능량 처리

**확정(2026-11-11):** 하루 생성 가능량은 생성 성공 기준으로 차감한다(4.2에 반영). 할당 가능한 배송지가 없어 생성에 실패하면 생성 시스템 자체가 종료되므로 이후 차감은 발생하지 않는다.

### 4. 시간 초과 손실과 배송 실패 페널티의 중복 적용

배송 제한 시간이 초과된 물류가 영업 종료까지 배송되지 않은 경우 다음 두 손실이 함께 적용되는지 확정이 필요하다.

- 시간 초과 손실
- 배송 실패 페널티

두 항목은 별도 손실로 구분하기로 했으나, 하나의 미배송 물류에 두 손실을 중복 적용할지는 명시되지 않았다.

**확정(2026-11-11):** 중복 적용하지 않는다. 시간 초과 손실은 배송을 완료한 물류에만, 배송 실패 페널티는 영업 종료까지 배송하지 못한 물류에만 적용한다.

### 5. 거리 추가 배송료 지급 조건

거리 추가 배송료는 배송 거리 기반 보상으로 결정되었지만 다음 조건은 확정이 필요하다.

- 제한 시간 내 배송 완료 시 지급 여부
- 제한 시간 초과 후 배송 완료 시 지급 여부
- 하루 종료 시 미배송인 경우 미지급 여부

권장 구조는 실제 배송 완료 시 지급하고 미배송 시 지급하지 않는 방식이다. 다만 이는 아직 확정된 규칙이 아니다.

**확정(2026-11-11):** 배송을 완료하면 제한 시간 내·초과 여부와 무관하게 지급하고, 미배송이면 지급하지 않는다.

## 16.7. 맵 메시·충돌 구성 및 최적화

**확정(2026-11-16).** 기술 조사 결과를 바탕으로 아래와 같이 결정하고 본문(10.2)에 반영했다. 정적 배칭은 렌더링 최적화이며 물리 충돌 메시와는 별개이므로, 두 문제를 구분하여 판단했다.

**조사 결과 (2026-11-16 기준)**

- 이음매 충격의 실제 원인은 바퀴 스피어캐스트가 타일 메시의 삼각형 경계에 닿아 기울어진 노멀을 반환하는 것이다. 메시를 하나로 합치는 것만으로는 해결되지 않으며, 접지면을 평면 BoxCollider(`MapGround`)로 대체한 것이 실제 해결책이다.
- 현재 베이크 도구(`MapColliderBaker`)는 도로 표면 높이(y = 0.03)의 삼각형만 접지면으로 보고 제외한다. 경사 타일(`road-slant*`, `tile-slant*`)과 다리·고지대 타일(`road-bridge`, `tile-high`)의 표면은 메시에 남으므로, 이 타일을 배치하면 이음매 충격이 다시 생긴다. 현재 맵에는 경사 타일이 없다.
- 렌더링 설정: SRP Batcher 켜짐, 정적 배칭 모든 플랫폼 꺼짐, GPU Resident Drawer 꺼짐, PC 렌더러는 Deferred. 도로 타일은 모두 하나의 `colormap` 텍스처 머티리얼을 공유한다.
- GPU Resident Drawer는 Forward+ 계열 렌더러에서만 동작하므로 현재 렌더러로는 사용할 수 없다.

**결정**

| 항목 | 결정 | 근거 |
|---|---|---|
| 충돌 구성 | 타일별 콜라이더로 돌아가지 않는다. 접지면은 단순 콜라이더(BoxCollider), 벽·연석·난간은 단일 베이크 메시로 분리하는 구조를 정식 방식으로 한다 | 이음매 충격을 실제로 해소한 구조이다 |
| 경사·다리 타일 | 경사·다리 타일을 맵에 배치하는 시점에 베이크 도구가 타일 종류별로 기울어진 접지 BoxCollider를 생성하도록 확장한다. 대안은 접지 노멀만 레이캐스트로 구하는 방식이며, 확장 시점에 선택한다 | 현재 맵에서 쓰지 않으므로 배치 시점에 함께 처리한다 |
| 렌더링용·충돌용 메시 분리 | 분리를 유지한다. 렌더링은 타일 원본 메시, 충돌은 베이크 결과를 사용한다 | 현재 구조가 이미 분리되어 있다 |
| 렌더링 최적화 | 1순위로 맵 타일을 Static으로 지정하고 정적 배칭을 켠다. 적용 전후 Batches·SetPass Calls를 비교 측정한다. GPU Resident Drawer는 렌더러를 Forward+로 바꿔야 하므로 정적 배칭으로 부족할 때만 검토한다 | 비용이 가장 작고, 단일 공유 머티리얼 구조와 잘 맞는다 |
| 베이크 작업 흐름 | 에디터 도구(`Tools/Over?Load!/맵 콜라이더 베이크`)를 유지한다. 맵 타일을 수정하면 베이크를 다시 수행하는 것을 맵 제작 절차에 포함한다 | 베이크 결과가 없는 씬은 이음매 충격이 생긴다 |
| 작업 대상 씬 | 실제 릴리즈 게임 씬이 만들어지기 전까지 `SampleMapDesign` 씬에서 베이크·정적 배칭 적용과 측정을 수행한다. 릴리즈 씬을 만들면 같은 절차를 그 씬에 적용한다 | 릴리즈 씬이 아직 없다 |

**미결정:**

- 정적 배칭 적용 전후의 실측 수치와, 그 결과에 따른 GPU Resident Drawer 검토 여부
- 경사·다리 타일 접지 처리 방식(기울어진 BoxCollider 생성 또는 레이캐스트 노멀)의 최종 선택

2. 하루 운영은 기본 09:00부터 18:00까지 진행한다.
3. 정적 물류는 하루 시작 시 모두 생성한 뒤 플레이를 시작한다.
4. 동적 물류는 하루 중 무작위 시점에 생성하며, 실제 생성 시점을 기준으로 다음 생성 간격을 결정한다.
5. 동적 물류는 영업 종료 2시간 전에 생성을 중단한다.
6. 동적 물류 생성 마감 이후에도 기존 물류의 상차와 배송은 가능하다.
7. 배송 제한 시간은 신속 배송(Express)에만 있으며, 생성 즉시 감소하기 시작한다. 일반 배송(Normal)은 제한 시간이 없다.
8. Express의 배송 제한 시간은 물류센터와 배송지 사이의 직선거리 및 배송 유형 계수에 따라 결정한다.
9. 배송지별 할당량은 하루 누적 기준이며, 배송 완료 후에도 복구되지 않는다.
10. 모든 배송지의 할당 한도 소진은 신규 할당을 제한할 뿐 하루 종료를 발생시키지 않는다.
11. 동적 물류 생성 시 할당 가능한 배송지가 없다면 동적 물류 생성 시스템을 종료한다.
12. 플레이어는 배송 순서를 자유롭게 결정하며, 중간에 물류센터에 복귀하여 추가 상차할 수 있다.
13. 상차와 하차는 물류별로 진행하며 상호작용 키를 유지해야 한다.
14. 상차 및 하차 중단 시 현재 작업 중인 물류의 진행도만 초기화하고 완료된 물류는 유지한다.
15. Express의 배송 제한 시간 초과는 배송 실패가 아니며, 시간 추가 보상 미지급 및 시간 초과 손실을 발생시킨다.
16. 영업 종료 시 미배송 물류는 폐기하고 배송 실패 페널티를 적용한다.
17. 모든 배송이 완료되면 하루 운영을 조기 종료한다.
18. 영업 종료 시에는 작업 도중이라도 즉시 운영을 중단하고 일일 정산으로 전환한다.
19. 현재 마일스톤에서는 단일 차량, 고정 배치된 월드 오브젝트(정적·동적), 고정 배송지를 사용한다.
20. 차량 및 물류센터 성장 시스템, 경찰 추격 시스템 등은 후속 개발 범위로 둔다.
21. 플레이어는 ctrl 키로 일반·고속 주행 모드를 전환하며, 두 모드는 최고 속도와 핸들링에서 차이가 난다.
22. shift 키 드리프트는 접지력과 회전 성능만 바꾸며, 별도 자원이나 페널티를 발생시키지 않는다.
23. 카메라는 차량을 뒤에서 따라가며, 장애물이 시야를 가리면 높이를 유지한 채 차량 쪽으로 당겨져 벽을 뚫지 않는다.
24. 1차 맵은 3×3 블록 도로 루프에 배송지 5곳·물류센터 1곳을 두고, 도로 1칸 2.25m 축척을 기준으로 제작한다.
25. 배송 유형(Normal/Express), 생성 방식(Static/Dynamic), 물류 특징(Fragile/Heavy/Large)은 서로 독립된 분류 축이다.
26. 물류에는 여러 특징이 함께 부여될 수 있으며, 특징이 많을수록 보상이 커진다.
27. Fragile은 충돌 시 내구도가 더 크게 감소하고, Heavy는 무게 한도를, Large는 적재 한도를 더 많이 사용한다. 이 효과는 적재 가능 여부 판정에만 쓰며 물리 시뮬레이션에 반영하지 않는다.
28. 차량은 적재 한도와 무게 한도를 각각 가진다. 적재 한도는 초과할 수 없고, 무게 한도는 초과 상한 `W_max`까지 개별 상차로 초과할 수 있다.
29. 같은 배송지의 물류는 Express(남은 제한 시간 짧은 순) → Normal(생성 순)으로 처리한다.
30. 차량 충돌은 속도 디버프·보상 직접 감소·경제적 페널티 없이, 적재된 물류의 내구도만 감소시킨다. 월드 오브젝트의 주행 방해 효과는 충돌 페널티와 별개이며 내구도에 관여하지 않는다.
31. 물류는 기준 내구도에서 특징별 감산값을 뺀 초기 내구도로 시작하며, 충돌로 현재 내구도가 감소한다.
32. 현재 내구도가 0이 된 물류는 폐기 물류로 전환되어 즉시 배송 실패가 확정되고, 목적지가 처분 장소로 재설정되며(UI·아이콘·나침반도 처분 장소를 가리킴), 처분 장소에서 처분할 때까지 적재 공간을 차지한다.
33. 하루 결과는 별 0~3개로 표시한다. 조건부 성공 비율 `S / N`으로 판정하며, 모든 물류가 조건을 충족하면 별 3개, 정산 금액이 음수면 별 0개, 발생 물류가 0개면 별점을 표시하지 않는다.
34. Express는 제한 시간 내 배송 완료만 별점상 성공이며, 폐기 물류는 별점상 실패다.
35. 충돌 내구도 감소는 내 차량이 받은 속도 변화량으로 판정하며, 하한선 미만은 무시하고 1회 상한과 쿨다운을 둔다. 적재 물류 전체에 같은 기준으로 감소시키고 Fragile만 감소 배율을 적용한다. 남은 내구도는 보상에 반영하지 않는다.
36. 차량이 끼이거나 뒤집히면 리셋 키(R 홀드)로 마지막 안전 지점에 복구하며, 대가는 짧은 조작 잠금 시간뿐이다. 접근 불가·이동 불가 상황은 레벨 배치 규칙으로 방지한다.
37. Fresh는 상차 완료 시점부터 신선도가 줄고, 남은 신선도에 비례한 신선도 보상을 받으며, 신선도가 0이 되면 폐기 물류로 전환되어 배송 실패가 확정된다. 처리 순서는 상차 Fresh → Express → 대기 Fresh → Normal이다.
38. 맵 충돌은 렌더링 메시와 분리하여, 접지면은 평면 BoxCollider, 벽·연석·난간은 단일 베이크 메시로 구성한다. 맵 수정 시 에디터 도구로 다시 베이크하며, 맵 렌더링은 정적 배칭을 1순위로 적용한다.
38. 무게 한도를 넘은 만큼 전진 최고 속도와 가속도가 선형으로 줄며(하한 있음), 보상·내구도·별점에는 영향이 없다.
39. 하루 운영 중에는 어떤 UI도 게임 시간을 멈추지 않으며, 같은 프레임의 시간 사건은 시간 판정(영업 종료·생성 마감·제한 시간)을 상·하차 완료보다 먼저 처리한다.
